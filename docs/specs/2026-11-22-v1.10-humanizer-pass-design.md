# v1.10 — Humanizer pass (short design)

## Intent

Résumés and cover letters from the plugin should not read as AI-written. Add a rewrite
pass that runs the user's installed `humanizer` skill over the draft, placed so the
reviewer and the factual validation both see the rewritten text.

## Approaches

- **Call the installed humanizer (picked by the user).** Least to write and tracks
  humanizer updates. Costs: runs only where humanizer is installed, and its full rule
  set has to be overridden where it clashes with résumé conventions.
- **Copy a résumé-safe subset of the rules into the plugin.** Works for every install,
  but is a fork that drifts from humanizer. Not chosen.

## Design

1. **Where it runs.**
   - `resume-optimizer`: new **Step 5b — Humanize**, between Step 5 (Optimize) and
     Step 6 (Review).
   - `cover-letter`: inside Step 5, after the draft and before the reviewer dispatch.
   - In both, Step 6 review and the validation step then run on the humanized draft,
     so any fact the rewrite moved is caught by the existing checks.
2. **How it is called.** Invoke `humanizer:humanizer` with the Skill tool in embedded
   mode (final text only, no audit), passing the draft text plus the guardrails below.
3. **Guardrails passed with the draft** (these override humanizer's own rules):
   - Every name, number, date, title, employer, degree, and technology stays verbatim.
     No new facts: this is already humanizer's rule, and restated here.
   - Résumé only: keep action-verb bullets with no subject ("Built X…"). Keep every
     `**bold**` keyword marker exactly where it is. Keep the en dash in date ranges
     (`Jun 2024 – Present`). Add no personality or first person.
   - Cover letter: personality is allowed, in the candidate's voice per
     `letter-voice.md`. The letter's existing rules still win where they differ.
4. **After it returns.** Diff the result against the pre-pass draft. Revert any change
   to a protected token (names, numbers, dates, technologies, bold markers). Recheck the
   bold budget (≤2 per bullet, ≤10 per page).
5. **Not installed.** If the Skill tool has no `humanizer:humanizer`, skip the pass.
   Say "Humanizer not installed, pass skipped" in Factual Validation, and suggest
   installing it once. The rest of the run is unchanged.
6. **Reporting.**
   - Changes Made (résumé) and Choices Made (letter) list what the pass changed, and
     which humanizer edits were reverted and why.
   - Factual Validation states whether the pass ran.

## Non-goals

- No copied rules file and no new script check at export. A mechanical check for
  dashes and stock words can come later if drafts still slip.
- No change to `match-analysis` (it writes no prose), review mode, or the export steps.
- The reviewer agent's brief is unchanged.

## Touched files

- `skills/resume-optimizer/SKILL.md`: Step 5b, Changes Made and Factual Validation lines.
- `skills/cover-letter/SKILL.md`: Step 5 addition, Choices Made and Factual Validation lines.
- `README.md`: optional humanizer dependency.
- `examples/sample-run.md`: mention of the pass.
- `.claude-plugin/plugin.json`: version 1.10.0.

## Left to the builder

The exact wording of the guardrail block, and whether it lives inline in each SKILL.md
or in one shared file both reference. A shared file is preferred if the two blocks
would otherwise repeat most of the text.
