# Resume Optimizer v1.8 — Preferences, Write-back, Reviewer Agent, ATS Check, Keyword Emphasis

**Date:** 2026-10-19
**Status:** Approved by user (chat)
**Baseline:** v1.7.0 (`main`, commit `d060bba`)
**Source:** [docs/review-2026-10-19-vs-ai-job-search.md](../review-2026-10-19-vs-ai-job-search.md), findings 1.2, 1.3, 1.7, 1.12 and section 3

## Summary

The review compared this plugin with MadsLorentzen/ai-job-search and found five places
where a run is weaker than it needs to be. None of them is a new document type; all of
them are rules and checks around the documents the plugin already writes.

1. **Preferences.** The dossier records facts about the candidate but has no place for the
   candidate's standing choices: page size, page limit, letter language, items that are
   never printed, items that are never trimmed, deal-breakers. So every run re-asks for
   application context, and personal rules live outside the plugin where validation cannot
   see them.
2. **Write-back.** A fact the user confirms during a run — a metric, an ownership detail,
   a date — is used for that run and then lost. The next run asks again, or writes the
   bullet without it. The other repo names this failure and makes write-back a standing
   rule; this plugin only offers it for Narrative material.
3. **Reviewer.** The hiring-manager screen and the letter's revision pass are performed by
   the context that just wrote the draft. A fresh context catches what the author no longer
   sees. The other repo dispatches an `application-reviewer` agent with the drafts inline
   and gets exact edits back.
4. **ATS check.** Nothing verifies the rendered résumé the way a parser reads it: contact
   details as literal text, a single column, a clean text layer, the posting's terms
   present.
5. **Keyword emphasis.** The writing guide forbids "random mid-sentence bolding", so no
   term is ever bold, and a six-second scan has nothing to land on. Bolding the posting's
   own terms helps when it is rare and honest; it hurts when it is decoration.

v1.8 adds all five under the plugin's existing evidence rules and without a new hard
dependency.

## Design decisions

| Decision | Choice | Rationale |
|---|---|---|
| Where preferences live | `## Preferences` section of `background.md` | One file to keep; every skill already reads the dossier; a separate file would be a second path to pass |
| Page size mechanism | `render.py --page-size A4\|letter` rewrites the template's `@page` rule | The skill never touches the template `<head>`; a string rewrite in the renderer keeps that invariant and tests offline |
| CV language | Field recorded, English only in 1.8 | The character-set rule and the ATS check are ASCII-based; localising headings is a later change. The letter language is fully supported |
| Write-back consent | Offer in the same turn, write only on an explicit yes, one offer per batch | The dossier is the candidate's own words; silent writes would make it a log of the model's guesses |
| Reviewer | One `application-reviewer` agent in `agents/`, read-only tools, drafts passed inline | Plugins auto-discover `agents/*.md`; one agent serves both documents because the contract (exact edits plus findings) is the same, only the lens differs |
| Reviewer prompt location | Persona and output contract in the agent file; dispatch mechanics in `shared/reviewer-brief.md`; skill reference paths passed as prompt text | Keeps both SKILL.md files short and respects the layering rule: `shared/` never links into `skills/` |
| ATS text extraction | HTML checks always; PDF text layer via pypdf, then Poppler `pdftotext`, else reported unverified | Preserves the no-install promise; Chrome's PDFs usually carry a clean text layer, so the HTML checks catch most problems on their own |
| Bold budget | Hard cap measured by `ats-check.py`: asked-for tools first, up to two phrases per bullet, 1–4 words, 10 per page, never in headers, entry lines, contact line (1.8.1: widened from one per bullet and 8 per page so a bullet naming two asked-for tools can bold both) | A rule the script can count is a rule the model follows; "not too much" is not |
| Deal-breakers in the verdict | Checked before the bands; a stated violation is a Skip that names the deal-breaker; silence raises an Information Request | The verdict is labelled Apply/Skip, so it should respect the one input that makes a role not worth applying to |

## A. Preferences

`shared/background-dossier.md` gains a `## Preferences` section, one labelled line per
field, every field optional with a default that applies when the section or the field is
absent:

| Field | Default | Read by |
|---|---|---|
| Page size | Letter | both export steps (`--page-size`) |
| Resume page limit | 1 | résumé trim loop and `ats-check.py --page-limit` |
| CV language | English | recorded; English only in 1.8 |
| Letter language | English | cover-letter Step 5 |
| Never printed | (none) | résumé Optimize step; e.g. GPA |
| Never trimmed | (none) | every rung of the trim ladder; e.g. personal website link |
| Work authorization to consider | (none) | match analysis; never on the page |
| Target company types | (none) | tailoring register, verdict reasoning |
| Deal-breakers | (none) | match-analysis verdict |

Rules: skills read the section silently and ask application-context questions only for
fields it does not cover; the values are the candidate's choices, not evidence about the
candidate; Never printed outranks any posting; Never trimmed items survive every trim pass
and the user is told when that protection forced a different cut. Bootstrap asks for them.

## B. Facts confirmed during a run

`shared/evidence-rules.md` gains a section with that name. When the user confirms,
corrects or supplies a fact that is not in the dossier, the skill offers in the same turn
to append it verbatim to `background.md` in the section it belongs to. It never writes
without an explicit yes, makes one offer per batch of facts, and never offers harvested
facts (the per-run rule in `background-dossier.md` stands). A skill that writes no files
lists such facts under Information Requests as worth adding. Every writing skill ends its
Factual Validation with a `**Dossier updates:**` line naming what was appended, what was
declined, or `None offered`, so an unlogged write is visible.

## C. Reviewer agent

`agents/application-reviewer.md` declares `tools: Read, Glob, Grep, WebFetch` and no
Edit, Write or Bash. It receives the draft, the posting, the factual record, the Step-3
table and the applicable Preferences inline, reads the reference files whose absolute
paths the dispatching skill names, and returns two parts:

- **Part A** — a JSON array of exact edits `{old_string, new_string, reason, note}` with
  `reason` in `keyword | reframing | style | grounding | structure`; `old_string` verbatim
  and unique; an empty array is valid.
- **Part B** — findings by category. Résumé: the four screening parts from
  `critical-review.md` plus a keyword line. Letter: hook, body, conclusion, generated-draft
  tells, and the four letter failures from `non-fabrication-letter.md`. Then Information
  Requests.

It never proposes a fact, number, name, date or relationship absent from the material; a
gap becomes an Information Request.

`shared/reviewer-brief.md` holds the mechanics both skills share: when to dispatch, what to
pass inline, how to apply Part A (only edits whose `new_string` adds no claim beyond the
material; grounding edits that remove or soften apply directly; accepted and rejected edits
recorded by reason; the skill's own validation re-run afterwards), and the fallback when
the Agent tool is unavailable (the same screen in the current context, labelled
"reviewed in-context"). The résumé skill's Step 6 becomes a Review step whose Part B is the
Hiring Manager Review; the letter skill's revision pass is performed by the reviewer.

## D. ATS check

`shared/ats-check.py DOC.html [--pdf DOC.pdf] [--keyword TERM …] [--page-limit N] [--json]`.

HTML checks run always: email as literal text in `.contact` (phone is a warning); no
images, icons, background images or tables; single column (flex only on `.entry-line`);
the bold budget below; a year on every entry; ASCII letters only outside emails and URLs.
PDF checks run when an extractor exists: no `(cid:NNN)` or U+FFFD garbage; the email in the
text layer; headings in document order; keyword coverage as `covered`, `html-only`,
`missing` or `unverifiable`. Exit 0 pass, 1 fail, 2 PDF part unverified. The script never
judges synonyms; the skill annotates each `missing` row from the Step-3 table as
`synonym-only`, `missing (have it)` or `missing (gap)`, and adds a term only where the
evidence supports it. Results go into a new **ATS Check** subsection of Factual Validation.

## E. Keyword emphasis

`writing-guide.md` gains a "Keyword emphasis" subsection replacing the blanket ban: bold
the tools and technologies the posting names, where a bullet shows them in use, and
otherwise a posting phrase the candidate genuinely carried — always verbatim and strongly
supported; up to two phrases per bullet, 1–4 words, at most 10 per page; never in headers, entry lines, the
contact line, or Skills values beyond the existing labels; never a whole sentence; never a
metric alone. The template gets an explicit `li strong` rule, the converter guards against
a bold tag inside an already-bold entry heading, and Changes Made lists every bolded term
with the posting phrase it mirrors.
